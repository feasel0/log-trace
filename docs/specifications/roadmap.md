We are designing a state-machine to represent the behavior of two Matter devices that talk to each other and run through a test scenario.  The goal is create a tool for identifying, based on a test iteration's logs, whether the test succeeded or failed.  And if it failed, give us some answers about exactly how it deviated from the expected "happy path" behavior.  This information will be used to provide a starting point for efforts to debug and fix the problem.


The "source logs" refers to:
    `controller_log_iteration_<##>_<YYYY-MM-DD_HH-MM-SS>.log` console log file for controller (containing the console output)
    `Dut_log_iteration_<##>_<YYYY-MM-DD>T<HH_MM_SS_tttttt>.log` console log file for dut (containing the console output).  I think the `tttttt` are ticks and i don't know if they have leading 0s; it's some kind of sub-second time unit.
    `controller_tcpdump_<YYYY-MM-DD>_<HH_MM_SS_tttttt>.pcap` pcap file for controller, containing the controller-side tcpdump
    `RPI-DUT_tcpdump_<YYYY-MM-DD>_<HH_MM_SS_tttttt>.pcap.bz2` pcap file for dut, containing the dut-side tcpdump.  This is compressed, and you should stream decode it.
    There is also a traffic report (generated by a module within this project).  This should be generated first if it doesn't already exist.  While this isn't technically a source log (it's a derived artifact), it should still be read and used by the model.  The traffic report has both a machine readable `.json` file and a human readable `.md` file.  The model should use the machine-readable version.

The traffic report should be generated first (files that summarize the results of isolating each message and finding traces of it in the source logs), if it doesn't already exist (check for both its md and its json file, and make sure both exist).  The traffic report should have both a machine-readable version (.json) and a human-readable version (.md).
In addition to generating traffic report summaries, this tool should also generate a report that indicates specifically how the behavior seen in the log source information matches or doesn't match that which we'd expect to see based on a model of ideal test behavior.
This tool should use a deterministic state machine model to describes correct behavior during an iteration based on the source logs.
There will be one model for each configuration, with the configuration consisting of 3 independent parts:
    - 1. test case (in this example `TC_Android_Pair`).  This can be read from the log path.
    - 2. hardware configuration (in this example `raspi-raspi` being the controller and dut respectively)
        -- this can not be obtained from the log path, but it can be gotten from a fixed mapping.  right now the mapping consists of:
            --- `ble-wifi` -> `raspi-raspi`
            --- `ble-thread` -> `raspi-nordic`
        -- this mapping should be stored in a config file `config/hardware_map.yaml`
    - 3. the communication method (in this example `ble-wifi` being the PASE and CASE transport types, respectively).  this can be read fromt he log path)
    - The determination of the model configuration is done by a function `config = resolve_config(iteration_dir) -> {test_case, comm_method, hw_config}`
The path of the given iteration directory looks like this `logs/MatterTest/<Communication Method>/<MM>-<DD>-<YYYY>_<HH>-<mm>-<SS>-<sss>/<Test Case>/<iteration number>`, where MM is month, mm is minute, SS is seconds, sss is milliseconds.


The tool should be runnable, taking an iteration directory path as its parameter.  It should load the appropriate model and then compare the source logs and traffic report to that model.
The model should capture 2 kinds of state behavior:
    Message order.  This kind of message is sent one way (and possibly retried several times before succeeding), then this kind of response is sent the other way (and possibly retried several times), then this next kind of message is sent one way (and possibly retried several times), and this next kind of response is sent the other way (and possibly retried several times), etc.
    Console log outputs.  If we're in a particular state these are the kinds of lines we should expect to see in the log.  And anything else that we see in the log at this point should stand out as a red flag.
        Every single line in both the controller and DUT console logs should be accounted for. Either they are normal and expected at the point in time where they occur, or they are unexpected and get red-flagged in the report so a human can follow up. No log line should be ignored.

        Definition: "accounted for"
            A console log line is "accounted for" if the model checker can associate it with either:
                - a particular state (i.e. "this line is emitted while the system is in state X"), or
                - a particular transition/event (i.e. "this line is emitted when event E causes a transition into state X"), including transitions into the same state (self-transitions).

            Put differently: there must exist a state or a transition in the final deterministic state timeline that explains why the line occurred.

        Required vs occasional log lines (naming TBD)
            Some log lines/patterns are expected to occur every time the system enters/occupies a given state ("required"), while others are only sometimes observed during successful iterations ("occasional").
            (We may choose better terminology than "occasional" / "required" later; keep the distinction.)

        "Noise" is often real behavior (retries / recovery)
            Many lines that might initially look like "noise" are actually evidence of a sub-process retrying until it succeeds.
            These should be modeled explicitly as part of the deterministic state machine, e.g.:
                - a state like: "waiting for mDNS to give us a value"
                - an event like: "mDNS failed but is trying again"
                - represented as a self-transition back into the same state
            This event may occur 0 times or multiple times (e.g. 4), and is not treated as unstructured noise.

        Handling lines that appear across many states/events
            We expect that most lines have affiliation with a specific state or transition; we do not assume there are lines that can truly appear anywhere with no affiliation.
            If we discover lines/patterns that appear in many different states or events, the training/reporting system must surface these to the user to decide:
                - "yes, this is ignorable noise in the future", or
                - "no, keep it associated with specific states/events" even if it must be associated with multiple possibilities.

The model will be trained on successful iterations.
We should have ground truth about whether the training is complete and unambiguous.  If the result of our training is that we have contradictory information (sometimes this log line appears during a certain state but other times it appears during a different state) we should not just accept that either one is ok.  We should have an answer for why this is happening, which means calling out situations like this to the human user and letting the human user figure out if it really makes sense to have this kind of uncertainty or multi-possibility situation.
    Our biggest goal here it to NOT MISS A PROBLEM.  I'd rather have false positives (flagging something as suspicious when it's actually fine) and have to manually readjust the model to fix them than to have false negatives (neglecting to flag suspicious behavior).

Training is fully bootstrapped from successful iterations (no manual skeleton)
    The model should be trained entirely from data in successful iterations.
    We do not want to manually pre-define a "skeleton" for each test case based on human knowledge, because we have very large volumes of successful iterations available.

Training dilemma: "successful" does not always mean "clean"
    It is possible for a test iteration to pass even if some minor problems/abnormalities occur.
    This creates tension:
        - If such abnormalities sometimes occur during successful iterations, the model should know about them so a human debugging failures can recognize that they CAN happen on a successful run.
        - But those abnormalities may still be important early-warning signals that correlate with failures (e.g. a bluetooth stack warning that sometimes recovers, sometimes doesn't).
    Therefore: the model must capture frequency/rarity, not just binary expected/unexpected.

Probabilistic weights on log lines/patterns (learned from successful iterations)
    For each state and transition, log patterns learned during training should have a frequency/probability/weight that indicates how often they appear in successful iterations.
    This enables two classes of red flags during checking:
        - "Impossible": log lines/patterns not known to occur in successful iterations for the inferred state/transition.
        - "Rare but possible": log lines/patterns that CAN occur in successful iterations, but are very uncommon, and should be surfaced as suspicious in failed iterations.
    Reports for failed iterations should include a summary of "rare but possible" lines observed, in addition to truly unexpected lines.

PCAP decryption assumption
    We assume the pcaps are always decryptable because they are generated with a known key and tshark will always be called with a profile that contains those keys.
    Therefore, we expect the decode layer to have access to:
        - message counter (message id)
        - exchange id
        - decrypted payload

The model analysis's output reports should be written to the same iteration directory as the traffic report and the source logs.  It should have the file name `model_report.json` for the machine-readable report and `model_report.md` for the human readable version.
    Machine readable contents
        config identification
        detected run metadata
        per-line classification summary
        per-state timing + confidence
        red flags with stable codes
    Human readable contents
        narrative summary
        state timeline
        “unexpected lines” grouped by state + near-by context

When training the model, we should also produce a report that goes in the `logs/training/reports` subdir of this project.  This consists of 2 report versions, a machine readable json version and human readable md version.
    The reports should contain whatever information you deem necessary to fully explain what happened during training and what kind of shape we're in to start using the model vs give it more training time.  It should talk about what happened during this training session, how good the model is looking overall, and any information that would help us to understand how the training is going and how much more data we will need to train it for release.
    One very important thing to include in both reports is contradictions in model training.  If some kind of indicator seems noisy or imprecise or contradictory I want the human or agent reading these reports to know about it so we can investigate.  I do not want noise getting baked into the model.  These devices are deterministic and non-random so they should be have 100% consistently in practice, so if we're not seeing consistent behavior in the logging (for successful runs) then that means our theory of the model is wrong and needs correcting.


--------------------------------------------------------------------------------
Deterministic state model and unified time alignment (codified decisions)
--------------------------------------------------------------------------------

This section codifies design decisions about the deterministic state machine model and timestamp alignment across all 4 source logs.


Deterministic state machine model (per configuration)
-----------------------------------------------------

The state machine proceeds deterministically:
    - At all times, we are in exactly one state.
    - At any point in the analysis, the checker should know exactly which state we are in.
    - If there is uncertainty about which event is occurring or which state a given event should transition into, that uncertainty indicates that the observed behavior is violating the model of normal successful operation, and it must be red-flagged.

The model is deterministic: for a given iteration directory and its source logs, the model checker will produce a single state timeline and a single classification for every console log line.

Each configuration (as returned by `resolve_config(iteration_dir)`) has its own model.

Model structure:
    The model is represented as a sequence of states `S0, S1, ...`, where each state defines:
        - Expected message events (derived from pcaps and/or the traffic report JSON)
        - Expected console log patterns for the controller console log
        - Expected console log patterns for the DUT console log
        - Transition conditions (what evidence indicates we should advance to the next state)
        - Retry allowance / bounded repetition (details to be finalized in a later section)
        - Invariants (events/lines that should never occur in this state; violating them is a red flag)

Acceptance and forbiddance:
    Each state can define:
        - accept rules: event patterns that are permitted in this state
        - forbid rules: event patterns that must not happen in this state

Deterministic tie-breaking:
    When multiple interpretations are possible (e.g. weak timestamp alignment), the checker must still pick one deterministic interpretation using stable tie-breakers.
    HOWEVER, any such ambiguity must be surfaced as a red flag (we prefer false positives).


Unified timestamp alignment (common timescale)
----------------------------------------------

Goal:
    Convert timestamps in all four source logs into a *single common timescale*.
    The controller console log's timestamp is the canonical timescale.

Assumptions:
    - Each individual source file has internally-consistent passage-of-time (monotonic-ish timestamps).
    - The 4 sources may have *different constant offsets* (no drift model in v1).
    - All 4 sources contain some kind of timestamp.

Definitions:
    - Each timestamp alignment is modeled as a constant offset.
    - “Apply the offset” means: convert a timestamp from source domain to target domain by adding the chosen offset.

Required behavior:
    - The system must perform a regression/estimation using *many known points of correspondence* (message occurrences visible in multiple sources) to compute offsets.
    - If the offset is not consistent / does not produce plausible ordering invariants after application, the system must fail loudly with a detailed explanation.


Step 1: Find console-to-pcap offset per device
----------------------------------------------

We compute two offsets as stepping stones:
    1) controller_console_to_controller_pcap_offset
    2) dut_console_to_dut_pcap_offset

For each device, compute console-to-pcap offset using message correspondences.

Correspondences:
    A “correspondence” is a message instance that can be identified in both:
        - the device console log, and
        - the device-side pcap stream.

Direction-dependent expected ordering (device-local invariant):
    - Incoming (remote -> this device): pcap should log it slightly *before* console.
    - Outgoing (this device -> remote): console should log it slightly *before* pcap.
    (This describes relative observation timing, not causality.)

Initial offset estimation algorithm (per device):
    1) Select a sample of outgoing messages (e.g. 6) spread across different parts of the iteration.
       For each sample message i, compute an offset candidate:
           offset_out_i = console_ts_i - pcap_ts_i
    2) Take the median of these outgoing offsets:
           median_out = median(offset_out_i)

    3) Select a sample of incoming messages (e.g. 6) spread across different parts of the iteration.
       For each sample message j, compute an offset candidate:
           offset_in_j = console_ts_j - pcap_ts_j
    4) Take the median of these incoming offsets:
           median_in = median(offset_in_j)

    5) Average the two medians to get the initial offset:
           offset0 = (median_out + median_in) / 2

Offset validation and refinement (per device):
    After computing offset0, validate it by applying it to *every message* with a correspondence across the device console and device pcap.
    For each corresponding message:
        - Convert pcap timestamp into console timescale using the offset.
        - Verify the direction-dependent invariant:
            incoming:  pcap_time_in_console_scale < console_time
            outgoing:  console_time < pcap_time_in_console_scale

    If violations remain, adjust the offset by small increments and re-evaluate until:
        - violations converge to zero, or
        - we determine no workable offset exists.

Failure behavior (per device):
    If no offset produces plausible invariants, fail loudly. The failure explanation MUST include:
        - the per-correspondence diffs used to produce offset candidates
        - the two medians (median_out, median_in)
        - the averaged starting value (offset0)
        - the values iterated over during refinement
        - for each tried offset: how many messages violated the invariant
        - the final “best guess” offset and its violation count


Step 2: Find controller-vs-DUT offset (device-to-device alignment)
------------------------------------------------------------------

Once both console-to-pcap offsets have been determined, compute the offset between controller and DUT logs so everything can be expressed in the controller console’s timescale.

For this step, we choose the console logs as the comparison domain (since they will be what we ultimately want to align to the controller console timescale).

Direction-dependent expected ordering (cross-device invariant):
    For matched message correspondences visible in both device logs:
        - Messages traveling controller -> DUT should be logged by the controller before they are logged by the DUT.
        - Messages traveling DUT -> controller should be logged by the DUT before they are logged by the controller.

Initial offset estimation algorithm (controller_to_dut_console_offset):
    1) Choose a sample of controller->DUT messages (e.g. 6) distinct from those used above.
       For each message k, compute offset candidates:
           offset_c2d_k = controller_console_ts_k - dut_console_ts_k
       Take the median:
           median_c2d = median(offset_c2d_k)

    2) Choose a sample of DUT->controller messages (e.g. 6) distinct from those used above.
       For each message m, compute offset candidates:
           offset_d2c_m = controller_console_ts_m - dut_console_ts_m
       Take the median:
           median_d2c = median(offset_d2c_m)

    3) Average medians:
           offset0 = (median_c2d + median_d2c) / 2

Validation and refinement:
    Apply the candidate offset to all corresponding messages visible in both logs and check the cross-device invariant.
    If violations remain, tweak the offset in small increments and iterate as with console-to-pcap alignment.

Failure behavior:
    As with Step 1, if no workable offset exists, fail loudly with a detailed diagnostic report including:
        - the sample point diffs, medians, the average
        - the refinement search path and violation counts
        - best guess offset and remaining violations

Note:
    This approach assumes constant offsets without drift.
    If we encounter evidence of drift (e.g. residuals that grow systematically with time), we should fail loudly and report it, rather than silently baking drift/noise into the model.

Future development note (tolerance / buffering / jitter):
    The direction-based ordering invariants ("incoming pcap slightly before console" and "outgoing console slightly before pcap") are expected to hold in general, but may be violated occasionally due to buffering, scheduling variance, log flushing, capture timing jitter, reassembly, etc.
    In v1 we will attempt strict enforcement and fail loudly when we cannot find a workable offset.
    After we test on real data, we may need to introduce a controlled tolerance model (e.g., allow a small number of bounded outliers, or allow small time-window overlap) while still surfacing any degraded alignment quality prominently in reports.
